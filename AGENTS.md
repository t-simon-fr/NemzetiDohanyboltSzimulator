# Repository working agreement

Read `Docs/WORKFLOW.md` before implementation and `Docs/Workflow/STATUS.md` when resuming. GitHub issues are the task source of truth; `Docs/CONTINUE.md` contains historical notes.

- Communicate in Hungarian; code, identifiers and commit messages stay English.
- Keep delivery lean: small playable slices, targeted checks while developing, then one combined full verification/WebGL build when the batch is stable. Repeat only for relevant source changes, failures or unresolved risks. Finish behavior before one visual refinement pass; stop when acceptance criteria pass. Keep documentation concise and link shared evidence. Documentation-only changes need a diff/link check, not a Unity build. See `Docs/WORKFLOW.md` section 2.1.
- One issue per independently reviewable feature or bug. Record observable acceptance criteria, dependencies and exclusions before editing. A user-approved batch authorizes its implementation without another approval prompt.
- Implement one coherent slice, inspect its diff, run the relevant checks, then commit it separately. Do not bundle unrelated features. Use a short feature branch/PR for new feature work; keep review focused on that issue. The user authorizes merging completed, verified work into main without asking again. Merge dependent PRs in order, preserve unrelated edits, respect required checks/reviews, and verify the resulting main content. Publication still requires a separate request.
- Before editing, choose documentation/tooling/runtime scope and name the affected checks. Use `Tools/Review-Docs.ps1` for relative Markdown links and `Tools/Verify-Project.ps1 -Suite <ids> -PlanOnly` to inspect targeted Unity selection. See `Docs/WORKFLOW.md` section 2.2.
- Use `Tools/Invoke-Pipeline.ps1` for Unity. Compilation must complete before entering Play; top-level transport success alone is not test success. Never present an old run as a fresh pass: carrying unaffected checks requires the baseline, changed paths and fresh proof for affected behavior.
- One owner may control Unity/Play/build in this project at a time. Use one agent by default; delegate only when the user or higher-level instructions authorize it, with explicit file ownership and integration responsibility. A role document is not evidence of an actual agent/review run.
- Add meaningful coverage for state, inventory and money invariants. Do not write tests that only mirror implementation or repeatedly run unrelated suites. Register maintained suites in `Tools/Verification/suites.json`; historical checks are not automatically current.
- For visible changes complete `Docs/Workflow/VISUAL_REVIEW.md`: capture actual Game view including GUI, inspect the images and exercise the changed interaction. Screenshots alone are not a visual pass. Record reviewer, observations, resolution, source fingerprint and evidence paths.
- Track implemented, Unity verified, visual verified, WebGL verified and published separately. Issue checkboxes must describe the achieved stage. A successful Editor test is not a WebGL or deployment result.
- Pages publication requires explicit authorization. Build a shipping player without the acceptance probe, record the source/cache version and verify GitHub Pages reports the exact publish commit as built. The user requests relying on completed local QA without repeating gameplay/browser tests for publication; record this policy explicitly. Current release and evidence belong in `Docs/Workflow/STATUS.md`, not these instructions.
- Preserve unrelated user files (`Assets/_Recovery/`, `Assets/_Recovery.meta`, `Data/`). Never regenerate the scene or restore user edits to get a clean diff.
- Keep production code readable; do not compress new classes/methods into long single lines. Never commit temporary scripts, tokens, Library, Builds or local reports. Repository tools must resolve paths from `$PSScriptRoot`, not a machine-specific drive.
